# 05. План реализации

План разбит на вехи M0–M7. Внутри вехи — задачи с ID. Одна задача — один коммит или небольшая серия коммитов и, когда работа идёт через PR на задачу, один PR.

Обозначения:
- **Оценка:** S — до ~200 строк кода или полдня работы агента; M — 200–600 строк, около дня; L — больше 600 строк или несколько модулей, 2–3 дня.
- **[D]** — задача зависит от материалов дизайна (`design/`, `docs/design/`). На момент составления плана дизайн v1 передан, поэтому [D]-задачи можно начинать; изменения дизайна после v1 — повод для задач-адаптаций.
- **[A]** — нужен автор: решение, доступ, люди (плейтест, химик, юрист).
- Колонка «Файлы» — главные затрагиваемые пути.

Ключевая развилка плана — **ворота G1** после M3: дети играют в прототип лабы 10+ минут сами и просят ещё. Если нет — дорабатываем лабу (M3-доработки), а не идём в M4–M5.

## Процесс работы с git

### Ветки

- `main` — стабильная ветка, из неё деплоится основной сайт. Защищена: изменения только через PR, обязательные проверки CI, одобрение автора, слияние squash или rebase (линейная история).
- `develop` — ветка интеграции этапа прототипа (M0–M3). Агент работает в ней, коммитит по задачам и регулярно пушит. Ревью автору — PR `develop → main` по вехам (основной агент открывает PR).
- После прототипа — короткие ветки на задачу от `main`: `<тип>/<ID>-<кратко>`, например `feat/m4-02-sort-screen`, `content/m5-01-lesson-1`, `fix/m2-04-drag-ipad`. Одна задача — один PR.
- Ветки дизайна и контента — по тем же правилам (`design/…`, `content/…`).

### Коммиты

- Формат Conventional Commits на английском, ID задачи в квадратных скобках: `feat(engine): rule matcher with priorities and groups [M1-05]`. Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `content`, `build`, `ci`, `chore`, `perf`, `style`.
- Сообщение — что и зачем; при необходимости тело с деталями и ссылкой на требование (`Implements FR-018`).
- Каждый коммит собирается и проходит тесты (по крайней мере в конце задачи).
- Сгенерированные файлы (`src/generated/`) в git не попадают.
- В конце каждого сообщения коммита — строки атрибуции, которые задаёт основная сессия (сейчас `Co-Authored-By` и `Claude-Session`).

### Пулл-реквесты на ревью автору

- Шаблон PR: что сделано (одним абзацем), ID задач, критерии приёмки чек-листом, **как проверить** (ссылка на превью, команды, сценарий), скриншоты или видео для UI, риски и что не сделано, чек-лист (тесты, линт, контент валиден, доступность, безопасность контента — для контентных PR).
- Размер: желательно ≤ 400 строк без учёта сгенерированного и контента (NFR-065); большие задачи режутся на подзадачи.
- Сначала зелёный CI, потом запрос ревью. Агент не сливает PR сам — сливает автор.
- Замечания ревью исправляются новыми коммитами в той же ветке; после одобрения — squash.
- Решения, принятые в ходе ревью, записываются в ADR или в `docs/00-context.md` (сначала контекст, если меняется ключевое решение).

### Проверка каждой вехи

Перед отчётом о вехе: `npm run lint`, `npm run typecheck`, `npm test`, `npm run content:check`, `npm run build`, `npm run test:e2e`; скриншоты работающего сайта в Playwright на 1440×900 и 1024×768 (и 768×1024 для лабы), сравнение с макетами `design/mockups/` и скриншотами `design/screenshots/`. Короткий отчёт: что сделано, что проверено, что дальше.
